# CLAUDE.md

@AGENTS.md

## Proyecto

Landing page + Wiki oficial de los universos narrativos del YouTuber **BorisaoBlois** (Universo Colosos, Capitán de Galeón, Ellos Llegaron). Todo el contenido de la wiki está en **español**. La estética es "Abyssal Submarine / Liquid Glass": fondo azul profundo, acentos naranja bioluminiscente, glassmorphism.

## Comandos

```bash
make dev          # levanta Postgres (docker compose) + next dev
npm run dev       # solo el dev server
npm run build     # OBLIGATORIO tras cambios: valida MDX + tipos TS
make start        # build + next start en :3131 (para demos; el dev server bloquea orígenes externos)
make share        # build + next start + túnel público con cloudflared (mostrar el sitio sin hosting)
npm run lint      # ESLint
npm test          # tests unitarios (node:test) de la lógica pura; con TEST_DATABASE_URL, también los de integración del panel
npm run check:content  # valida MDX, navegación, assets, novedades, encuestas y HERO_POOL
make db-up        # solo la base de datos
make db-shell     # psql (user: root, db: webboris)
npx prisma generate / migrate dev / studio
```

Producción (VPS de Hostinger, Docker Compose detrás del nginx del servidor): `docker-compose.prod.yml`, `Dockerfile` (Next `standalone` con `NEXT_OUTPUT=standalone`) y `deploy/` (`setup-vps.sh` la primera vez, `deploy.sh` para actualizar: copia con `backup.sh`, migra con el superusuario y deja la app con el usuario de privilegios mínimos de `db-app-role.sh`). Guía en `docs/deploy/vps.md`. La imagen copia `src/content` porque las fichas se leen del disco al revalidar.

Validación: `npm run lint`, `npm test` (node:test sobre `tests/**/*.test.ts`), `npm run check:content` y `npm run build` (parsea todos los MDX y chequea tipos). El CI ejecuta los cuatro. `tests/integration/` (escrituras del panel contra Postgres) solo corre con `TEST_DATABASE_URL`, una base desechable y migrada cuyo nombre acabe en `_test` (el test se niega a correr si no; cómo crearla, en la cabecera de `cms-store.test.ts`); sin ella se marcan como saltados. El CI la levanta como servicio (`postgres:17-alpine`, `webboris_test`) y la migra antes de `npm test`.

## Stack

Next.js 16 (App Router) + React 19 · Tailwind CSS v4 (`@import 'tailwindcss'`) + shadcn/ui · Prisma v7 con driver adapter `@prisma/adapter-pg` (PostgreSQL) · Auth.js v5 (middleware en `src/proxy.ts`, convención Next 16) · TanStack Query v5 + Zustand v5 · Zod v4 · MDX vía `next-mdx-remote-client/rsc` + `gray-matter`.

Consulta la documentación oficial (context7 MCP o `node_modules/next/dist/docs/`) antes de implementar features con Next.js 16, Prisma v7 o Zod v4 — sus APIs difieren de versiones anteriores.

## Arquitectura

Dos grupos de rutas en `src/app/`: `(marketing)` (landing) y `(wiki)` (la wiki; el menú lateral es `AppSidebar`, montado en el layout de `/wiki`).

### Pipeline de contenido de la wiki (lo más importante)

El contenido NO está en la base de datos: son archivos MDX planos.

1. `src/content/*.mdx` — un archivo por artículo; el nombre del archivo es el slug de la URL (`/wiki/<slug>`). Lo publicado en el panel `/admin` va por encima de estos archivos (ver «Contenido del panel»).
2. `src/utils/mdx.ts` — `getAllArticles` lee los archivos, parsea el frontmatter con `gray-matter` y lo valida con `WikiFrontmatterSchema` (Zod) de `src/core/types/wiki.ts`. Si el frontmatter no pasa el schema, el artículo se omite (404 silencioso) — revisar la consola del server. Fuera del repositorio nadie importa `@/utils/mdx`: los artículos se leen con `getContentRepository().getArticles()` / `.getArticle(slug)` (`src/core/content/`), el punto de cambio para un futuro CMS.
3. `src/app/(wiki)/wiki/[slug]/page.tsx` — renderiza vía `WikiArticleHeader` / `WikiArticleContent` / `WikiArticleFooter` (en `src/features/monsters/components/wiki/article/`).
4. `MdxRenderer.tsx` (`src/features/monsters/components/wiki/mdx/`) — registro de componentes disponibles dentro de los MDX: `WikiImage`, `WikiGallery`, `WikiQuote`, `WikiInfobox`, `InfoField`, `WikiTOC`, `AbyssalAlert`, `AbyssalTable`, `RegistroDelirium`, `Proximamente`. Un componente usado en un MDX pero no registrado ahí (y en `src/mdx-components.tsx`) rompe el render.

**La navegación del sidebar**: la de los archivos es `WIKI_NAVIGATION` (`src/features/monsters/config/wiki-navigation.ts`, datos puros con iconos por nombre, `NAV_ICON_NAMES`); el panel puede publicar otra por encima (lista `navigation`, `/admin/contenido/menu`). **Siempre se lee con `getContentRepository().getNavigation()`**: el layout de la wiki se la pasa a `AppSidebar` → `SidebarNavigation`, y la usan `ArticleNeighbors` y `getRelatedArticles` (último parámetro). Esquema y reglas en `src/core/content/navigation.ts` (`NavigationSchema`, `navigationProblems`: fichas que existan, sin repetir, sin grupos `#` vacíos, ≤ 3 niveles), que comparten `check:content` (importa `WIKI_NAVIGATION`, ya no lo lee como texto) y el panel. Los iconos se convierten en componentes en `src/components/sidebar/nav-icons.ts`. Al crear un artículo en el repositorio hay que añadir su entrada en `wiki-navigation.ts`; uno creado en el panel se añade desde el editor del menú («Fichas que no están en el menú»). El orden de `WIKI_NAVIGATION` define también Anterior/Siguiente (`ArticleNeighbors`: hermanos dentro del grupo padre inmediato, con vuelta al principio; en un grupo de 2 solo hay «Siguiente»).

**Artículo de referencia**: `src/content/the-bloop.mdx` es el estándar de oro — frontmatter completo (infobox con secciones, description, imageCaption), secciones `##` (Características / Alimentación / Personalidad / Referencias), `WikiImage` con `align` alternado. Los artículos nuevos deben seguir ese formato.

**Solo canon, nada inventado**: el texto, los pies de foto y las citas (`WikiQuote`) deben salir de `docs/Frases y descripciones.docx` o `docs/Requerimientos Pagina.pdf`. Si un apartado no tiene información, va `<Proximamente />`; si el artículo entero no la tiene, `status: proximamente` en el frontmatter: chip y, en lugar del bloque Próximamente, `ExpedienteSellado` (sello, «Boris aún no ha desclasificado este expediente.» y los enlaces «Pide que se desclasifique» —solo en la semana de su votación—, «Sigue el canal» y «Ver el registro»). Una ficha no sellada con ≥ 2 apartados `##` (sin contar Referencias), alguno de ellos solo con `<Proximamente />`, muestra `ArchivoMeter` («N de T apartados desclasificados»). Una imagen solo se usa si muestra lo que dice el apartado; si no hay imagen concreta, `<WikiImage alt="…" caption="…" />` sin `src` (marcador "Imagen pendiente") o portada omitida (placeholder por categoría). Nunca el logo ni el esquema del sitio como portada.

**Ficha estándar** (spec `docs/superpowers/specs/2026-10-27-fichas-estandar-design.md`): toda ficha que no es índice lleva siempre el rail, cuya ficha lateral empieza por la sección automática «Expediente» (`Universo`, `Categoría` y, en las selladas, `Estado: Sellado`, sacados del frontmatter; una sección «Expediente» del `infobox` se funde en ella). Las no selladas llevan `description`, `imageCaption` si hay `image`, un `infobox` con al menos una sección propia y al menos dos apartados `##` (sin contar Referencias) según su tipo: Coloso/Titán/Animal/Especie → Características · Comportamiento · Alimentación; Humano → Biografía · Trayectoria · Relaciones; Organización → Origen · Financiación y recursos · Miembros; Vehículo → Características · Registro operativo; Historia/Entidad → Sinopsis · Acontecimientos. Lo exige `check:content` (`checkArticleStandard`, `src/core/content/validate.ts`).

**Contenido del hub `/comunidad`**: `src/content/novedades/<yyyy-mm-dd>-<slug>.md` (frontmatter `fecha`, igual a la del nombre del archivo; `titulo`; `resumen` ≤ 160; `enlace` interno o `https://` de YouTube, `NEWS_HOSTS`; sin cuerpo; un YAML roto se registra y se salta) y `src/content/encuestas.json` (votaciones curadas `{ semana: "YYYY-Www", tipo?, a, b, pregunta? }`; las semanas sin votación curada rotan solas con duelos; publicar a mitad de semana una ficha con `stats` cambia ese duelo automático y reinicia su recuento, así que un duelo que deba mantenerse va en `encuestas.json`). `tipo` es `duelo` (por defecto; a y b con `stats`) o `desclasificar`: en las semanas futuras, a y b deben tener `status: proximamente`; ese tipo de votación no lleva Arena, y la ficha sellada muestra «Pide que se desclasifique» esa semana. El id de la encuesta es `<semana>-<a>-vs-<b>`: renombrar un slug cambia el id de sus encuestas y sus votos. Se leen siempre vía `getContentRepository()` (`src/core/content/`), el punto de cambio para un futuro CMS. `check:content` valida ambos. La criatura de la semana (`pickFeatured`, en el hub) y la encuesta cambian a la vez: el lunes a las 00:00 UTC (semana ISO en UTC, `src/core/content/iso-week.ts`). Orden de `/comunidad` (spec 2026-10-27): novedades (la más reciente destacada, con la imagen deducida de su enlace: portada de la ficha o miniatura de YouTube, `newsImage`), encuesta (con «Próxima semana» al pie, `getNextPoll`), criatura de la semana, últimos vídeos (hasta 4, `latestVideos` sobre `getChannelVideos`), historial de votos y «Tu registro» (`RegistroProgress`). En escritorio la columna mide `max-w-6xl` y se reparte en horizontal: novedades en dos columnas (destacada | lista), encuesta (3/5) junto a la criatura como tarjeta (2/5), vídeos en cuatro columnas y el historial en una fila; en móvil, todo en una columna. El historial (semana pasada —la semana ISO anterior; sin votos, no aparece—, palmarés y expedientes más pedidos) se deduce de `PollVote` por `pollId` con un solo `groupBy`: `summarizeHistory` (`src/features/community/lib/poll-history.ts`) ← `GET /api/comunidad/historial` (sin caché; ante un error registra una línea y responde vacío) ← `PollHistoryTiles` (cliente, bajo el pliegue; sin datos no pinta nada). `parsePollId` parte el id por el primer `-vs-`, así que ningún slug puede contener `-vs-` ni acabar en `-vs` (lo rechaza `check:content`). No borres las entradas pasadas de `encuestas.json`: el historial deduce de ellas el tipo de cada encuesta (`desclasificar` o `duelo`).

**Vídeos de «Aparece en»**: `src/content/videos.json`, `[{ id (11 caracteres), fichas: [slug…], titulo? }]`, son las relaciones manuales vídeo ↔ ficha. Las menciones en el título del vídeo se detectan solas (`linkVideos` con las reglas de `findMentions`). Un id que no está en `FEATURED_VIDEOS` (`src/features/marketing/config/videos.ts`) necesita `titulo`. Se lee con `getContentRepository().getVideoLinks()` y lo valida `check:content`. La lista «vídeo → criaturas» que mande Boris va aquí (solo lo que el título del vídeo no dice).

**Orden de la historia**: `src/content/orden-historia.json` (opcional; **no existe** hasta que Boris lo mande), `[{ universo, ids: [videoId…], nota? }]`: `universo` es un `universeKey` de `universes.ts` y cada id debe estar en `canal.json` (lo valida `check:content`). Con una entrada, `/videos` ofrece una tercera opción «Orden de la historia» (`?orden=historia`, `storyOrderVideos`: la lista de Boris y luego el resto del grupo) y `/empieza-aqui` muestra «Empieza por este vídeo» con su primer id (`storyStarts`); sin archivo, nada cambia. Se lee con `getContentRepository().getStoryOrder()`.

**Lista del canal**: `src/content/canal.json` (`[{ id, titulo, tipo: video | short, orden, fecha?: YYYY-MM-DD }]`; vídeos y luego shorts, cada bloque por `orden`, el puesto de publicación dentro de su tipo, 1 = el más antiguo) es la instantánea completa del canal y la base de `getChannelVideos` (con `FEATURED_VIDEOS` y el RSS, que solo trae los últimos 15 y a menudo da 404). La genera `npm run sync:canal` (`scripts/sync-channel.mts`, sin clave de API): por defecto solo lista las pestañas «Vídeos»/«Shorts» (de ahí sale `orden`) y conserva las fechas ya conocidas; `-- --con-fechas` pide además la fecha de los que no la tienen, de uno en uno, y ante un 429 o un fallo deja de pedirlas y guarda lo que tiene. Si falla el listado no toca el archivo. **Repetirlo antes de cada despliegue** para recoger lo publicado. La valida `check:content` (`orden` entero positivo sin repetir dentro de su tipo; `fecha` válida si la hay). El orden de publicación (`sortVideosByDate`, también en `latestVideos`): por fecha cuando la hay y, dentro de cada tipo, por `orden`; la fecha solo se muestra si se conoce (si no, «Short» o nada). Con el RSS caído, «Ver el último vídeo» de la landing enlaza al vídeo de mayor `orden` de `canal.json` (`getLatestVideo`, `source: 'canal'`). `/videos` la agrupa por universo (fichas vinculadas → palabras clave del título, `universe-keywords.ts` → «Otros vídeos»).

Frontmatter (ver `WikiFrontmatterSchema`): `title` y `universe` obligatorios; opcionales `image`, `imageCaption`, `category`, `description`, `infobox` (récord de secciones → pares clave/valor) y `stats` (length, weight, intelligence 1-10, hostility 1-10, power/defense 0-100, biteType, specialAbilities).

Otros campos opcionales del frontmatter: `aliases` (apodos canónicos con los que la búsqueda y los enlaces automáticos reconocen la ficha; **solo con fuente canónica**, ver la spec de la Ola B §6, y las variantes sin confirmar no entran) y `related` (slugs de relacionados, con el orden fijado a mano; mandan sobre el ranking automático). `check:content` rechaza un apodo duplicado, un apodo igual al título de otra ficha, un apodo vacío y un `related` inexistente, repetido o que apunte a la propia ficha.

`faq` (opcional, `[{ pregunta, respuesta }]`, ≤ 10, sin vacías ni repetidas: `FaqSchema`): solo respuestas de Boris. Con preguntas, `ArticleFaq` pinta «Preguntas frecuentes» (lista de `<details>`) al final del cuerpo, antes de «Aparece en», con su entrada en el índice, y la página emite el JSON-LD `FAQPage` (`faqJsonLd` + `serializeJsonLd`, `src/features/monsters/lib/faq.ts`). No es un apartado del MDX: no cuenta para `ArchivoMeter` ni para `checkArticleStandard`, y `check:content` rechaza una ficha con `faq` que además tenga «## Preguntas frecuentes» en el cuerpo. Hoy ninguna ficha lo usa.

### Otras piezas

- `src/features/` — módulos por dominio (`monsters` es el de la wiki; también `marketing`, `auth`, `payments`, `community` (hub /comunidad)).
- `src/features/monsters/actions/get-wiki-articles.ts` — server action de listado con búsqueda/filtros/paginación (filtra en memoria sobre los MDX). En `WikiList`, las pestañas, el universo y la página crean entrada de historial (`pushState`) y el texto del buscador la reemplaza; si la consulta falla, se muestra «Reintentar» en lugar de «Ningún registro coincide».
- `src/core/` — server actions globales, config de Auth.js, tipos.
- `src/core/search/` — lógica pura (imports relativos `.ts`, probada con node:test): `tipos` (agrupación de categorías: una categoría nueva del frontmatter debe añadirse a `TIPOS`, lo exige `tipos.test.ts`) y `catalog` (el catálogo excluye las páginas `Directorio`/`Categoría`). La `image` del frontmatter se muestra como imagen de cabecera de la ficha salvo que el cuerpo MDX ya la use o la ficha sea un índice (`Directorio`/`Categoría`). Además:
  - `entity-index`: índice de entidades (título, apodos, categoría, `richness`…) y `findMentions`. La regla del nombre propio: un nombre de una sola palabra solo cuenta si en el texto empieza en mayúscula; los de varias palabras valen siempre. Solo se enlazan las categorías de `LINKABLE_CATEGORIES`. Las contracciones «del» / «al» cuentan con los nombres que empiezan por «El» si la palabra siguiente va en mayúscula: «del [Ángel]», «al [Gran Majá]».
  - `search`: la búsqueda única de la paleta (⌘K) y del explorador (`getWikiArticles`): palabras en cualquier orden (tokens), apodos y erratas (distancia de edición 1 desde 5 letras); `suggest` da el «¿Quisiste decir…?». `MAX_QUERY_LENGTH` acota la consulta.
  - `mention-graph` + `related-rank`: el grafo «quién menciona a quién» y el orden de los relacionados de la ficha (`related` a mano → menciones → hermanos del menú → categoría → universo; las Próximamente al final). Los construyen `getEntityIndex()` / `getMentionGraph()` (`src/core/content/entities.ts`, en caché por petición).
  - `extract-body-text`: saca la prosa de un MDX (sin código, etiquetas JSX ni imágenes) y sus enlaces manuales `/wiki/…` para el grafo de menciones.
  - `registro` (`registroEntries` / `registroSlugs` / `progress`): cuentan las fichas que no son índice ni `proximamente`, y es el mismo conjunto que usa el aleatorio.
  - `section-completeness`: apartados `##` con contenido frente a los que solo llevan `<Proximamente />` (alimenta `ArchivoMeter`).
  - `nav-neighbors` (+ `groupLabel`): fichas vecinas en el menú para Anterior/Siguiente.
  - `random-pick`: el sorteo del expediente aleatorio (con la ficha de origen excluida).
  - `video-links`: relaciona vídeos y fichas (`linkVideos`).
  - **Regla:** una categoría nueva del frontmatter debe añadirse a `TIPOS` **y** decidirse en `LINKABLE_CATEGORIES` (si tiene nombre propio y se enlaza, o no).
- `src/utils/remark-entity-links.ts` — plugin remark que `MdxRenderer` aplica al MDX: enlaza la 1.ª mención en prosa de cada entidad en toda la ficha. No entra en títulos, enlaces, código ni en `WikiImage`/`WikiGallery`/`WikiTOC`/`Proximamente`/`WikiInfobox`/`InfoField`, ni en `<a>`, `<code>`, `<pre>` o `h1`-`h6` escritos como JSX. Un enlace manual a la misma ficha gana: no se añade otro.
- `src/components/search/` — la paleta de búsqueda: `SearchPaletteHost` (montado una vez en el layout raíz; atiende ⌘K / Ctrl+K y carga `SearchPalette` con `next/dynamic` en la primera apertura; si ese chunk no llega, cierra y avisa con «Recargar» en lugar de romper la página; no se abre encima de otro modal), `SearchTrigger` (los disparadores del layout de la wiki, la navbar y el hero de la landing; precargan la paleta al pasar el ratón o el foco) y `useSearchPalette` (estado Zustand).
- Visor de imágenes de la ficha — `ArticleImagesProvider` / `ViewerLink` en `src/features/monsters/components/wiki/mdx/ArticleImages.tsx`: reúne las imágenes del cuerpo (`data-viewer-src`) y abre `ImageViewer`; empuja una entrada al historial para que «atrás» lo cierre.
- Estado del fan — `useRegistro` (`src/features/monsters/store/registro-store.ts`), en `localStorage` con la clave `wb-registro`, solo en el cliente. Se pinta con `useSeen` / `useIsSeen`, que muestran el estado neutro hasta hidratar; nunca se lee en el servidor. Lo escribe `MarkSeen` en la ficha, y solo en las no selladas.
- Rutas propias de la wiki — `/wiki/registro`: página con ISR de 1 h. `/wiki/aleatorio`: route handler `force-dynamic` que responde 307 con `no-store`; nunca lleva a índices ni a sellados, ni a la ficha de origen, y todo `<Link>` a esta ruta lleva `prefetch={false}`. `arena`, `registro` y `aleatorio` son nombres reservados (`RESERVED_SLUGS`, `src/core/search/wiki-routes.ts`): ningún MDX puede usarlos, lo comprueba `check:content`. En ese mismo archivo vive `WIKI_LINK`, la forma de una URL interna de ficha (`/wiki/<slug>` con `/`, `?` o `#` detrás): la comparten el plugin de enlaces y el grafo de menciones.
- Ficha `[slug]/page.tsx` — `revalidate = 3600`, por la encuesta semanal y el RSS, y `dynamicParams = true`: las fichas de los archivos salen del build y las creadas en el panel se generan en su primera visita; un slug que no existe responde un 404 real. Orden de montaje: `ArticleProgress`, `MarkSeen`, cabecera, contenido (`ArchivoMeter` / cuerpo / `ExpedienteSellado`), `SectionChip`, `EntityPreview` y un bloque de cierre `data-related` (`ApareceEn`, `ArticleNeighbors`, pie); ese `data-related` es donde se oculta `SectionChip`. `EntityPreview` previsualiza los `a[data-entity]` y comparte la consulta `['wiki-index']` con la paleta. «Aparece en» sale de `getVideosForSlug` (`src/features/community/data/channel-videos.ts`); `youtube-rss.ts` es el fetch compartido del feed: reintenta hasta 2 veces ante 404, 5xx, un fallo de red o el tiempo límite (`withRetry`, unos 6 s en total, porque el feed de YouTube responde 404/500 al azar) y recuerda el fallo final 60 s (`memoizeFailure`). El tiempo límite se impone con `abortable` además del `signal`, porque Next quita el `signal` del `fetch` cuando revalida una entrada caducada de su caché.
- Renombrar un slug — `git mv` + `redirects()` en `next.config.ts` + `LEGACY_SLUGS` en `src/features/monsters/components/arena/resolve-pair.ts` + actualizar encuestas, vídeos, navegación y enlaces de los MDX.
- `src/components/content/` — primitivas del rediseño minimalista (#55): `ContentCard`, `Section`, `FactsLine` y `PendingLabel` (el rótulo de texto «Próximamente»). La portada de una tarjeta o ficha sale de `coverOf(image)` (`src/components/content/CategoryPlaceholder.tsx`, que también dibuja el placeholder por categoría), que descarta las imágenes de marca; los componentes cliente importan cada primitiva de su archivo (`@/components/content/PendingLabel`…), no del barril, para no arrastrar `ContentCard` al bundle del cliente. En una `ContentCard` con `href`, el enlace es el título y su `::after` cubre toda la tarjeta (patrón de enlace estirado): el nombre del enlace es el título (más el aviso de pestaña nueva), y la meta y la descripción son su descripción accesible. Un elemento interactivo que se añada dentro de una tarjeta necesita `relative z-10` para quedar por encima de ese `::after`. Para vídeos y fechas: `youtubeWatchUrl` / `youtubeThumbUrl` (`src/utils/youtube.ts`) y `formatFecha` (`src/utils/format-date.ts`).
- Embudo a YouTube (auditoría UX 2026-10-29, `docs/audits/2026-10-29-ux-recien-llegado/`): «Suscríbete» usa `YOUTUBE_SUBSCRIBE_URL` (`sub_confirmation=1`, `social.ts`) en el hero, las fichas y el pie. La ficha muestra bajo el título una línea de contexto (universo · serie de BorisaoBlois · Ver en YouTube), la escala `blueWhales` (`src/features/monsters/lib/scale.ts`, 30 m por ballena, desde 60 m) junto a la longitud y, si tiene vídeos (`getVideosForSlug`), «Aparece en vídeo» justo tras la cabecera con `YouTubeLite` (`src/components/content/`): miniatura y botón; el `iframe` de `youtube-nocookie` solo se carga al pulsar. `/wiki` abre con «Empieza por aquí» (`START_HERE`, `src/features/monsters/config/start-here.ts`; `check:content` exige slugs existentes y no sellados), oculto con búsqueda, filtros o página > 1.
- Landing `(marketing)/page.tsx` — orden: hero (con «Ver el último vídeo» y «Suscríbete», `HeroActions`) → vídeos → universos → personajes → comunidad → sobre Boris; **dinámica** (ƒ, sin `revalidate`): `HeroAbisal` sortea en cada visita un expediente de `HERO_POOL` (`src/features/marketing/config/hero-pool.ts`) con `pickHeroCreature` (`lib/hero-pick.ts`, puro) tras `await connection()`, todo en `getHeroCreature` (`data/hero-creature.ts`, que devuelve `{ creature, image, imagePosition }`): el `Math.random()` va ahí y no en el componente, porque `react-hooks/purity` lo rechaza durante el render. ## Estándares de diseño ("ley Abisal")

- Paleta: primario `#FF7300` (naranja), fondo `#00122E`, gradientes `#00203F`→`#00162D`, cian `#0064A0`, texto blanco/70%.
- Tarjetas: `ContentCard`; secciones: `Section`; datos: `FactsLine` (`src/components/content/`). Una sección = un propósito (h2 + contenido + como mucho "Ver todo"); sin eyebrows por tarjeta ni por sección; iconos solo funcionales. Superficie `crystal-surface` (es `position: relative` y su `::after` dibuja el hilo de brillo superior: no usar `after:*` en un elemento con esa clase, y un hijo `absolute` se coloca respecto a ella); `.glass-liquid` solo en navbar, footer y botón secundario; superficie sólida `#061a2e` bajo texto largo.
- Headers MDX (`h2`/`h3`) deben mantener `clear-both` (evita solaparse con `WikiImage` flotados).
- Las ilustraciones (`<Image>` de arte) usan `quality={IMAGE_QUALITY}` (85, `src/utils/image.ts`), listado en `images.qualities` de `next.config.ts`; las miniaturas de vídeo son `sddefault` (640×480; la caja 16:9 recorta las barras).
- Las imágenes llenan su contenedor edge-to-edge, sin padding interno.
- Assets físicos en `public/assets/` usan guiones bajos, nunca espacios (`The_Bloop`, `El_Gran_Maja`, …), organizados por entidad del lore.
